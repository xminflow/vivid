# 说明
这是多个小程序以及一个后端管理系统，后台管理系统统一管理所有的小程序后台数据

# AI 协作原则

- AI 必须优先理解现有代码、架构和上下文，不得在未确认事情的情况下直接改造
- 当需求目标、影响范围、数据来源、验收方式、异常处理任一项不明确时，必须先向用户澄清，但如果你能够从源码中知道结论，则不要提出多余问题
- 对开发、调试、修复、重构、规格生成类任务，必须建立明确验收标准，并在完成后验证
- 普通咨询、代码解释、规范讨论类任务不强制修改代码，但必须给出清晰结论和依据
- 如果发现不合理代码、架构偏差、重复实现、临时方案或潜在风险，必须明确告知用户，并提出改进建议
- 禁止为了快速完成任务而引入临时补丁、隐式兜底、重复逻辑或不必要依赖
- 禁止覆盖、回滚或删除用户已有修改，除非用户明确要求
- 每次完成任务后，必须说明完成内容、验证方式、遗留风险


# 需求与验收标准

- 每个开发任务都必须有可检查的验收标准
- 验收标准应优先使用自动化方式，例如测试、类型检查、lint、服务启动、接口调用或日志验证
- 如果无法自动验证，必须说明原因，并提供人工检查步骤
- 修复类任务必须说明问题根因、修复方式和验证结果
- 如果同一个问题此前已修复但再次出现，必须分析上一次修复失败的本质原因
- 不允许只凭代码改动判断任务完成，必须结合测试、日志、接口结果或运行状态确认

# 代码修改边界

- 遵循最小化实现原则，只实现当前需求必要内容
- 新增或升级依赖必须先获得用户批准
- 禁止引入未批准的技术栈、框架、服务或外部平台
- 禁止静默兜底；如确需降级策略，必须显式设计、记录日志，并获得用户批准
- Python 代码必须使用明确类型标注，禁止无约束动态类型
- TypeScript 代码禁止滥用 `any`，必要时必须说明原因并限制作用范围
- 代码应高内聚、低耦合，避免硬编码、重复代码和跨层依赖
- 复杂业务逻辑、架构边界、异常处理和非显然设计必须添加中文注释
- 不应为简单赋值、直观流程添加低价值注释
- 生成的文档、规格说明、任务说明默认使用中文

# 开发规范

- 前端采用 feature-based 结构。
- 后端采用 DDD + 整洁架构。
- 后端业务逻辑不得直接依赖基础设施实现。
- 外部服务、数据库、缓存、第三方 API 必须通过基础设施层适配。
- 应用层负责编排用例，不应承载底层技术细节。
- 领域层应表达核心业务概念、规则和接口。
- 前端组件应优先复用，样式必须通过主题系统或既有设计规范管理。
- 不允许为了单个页面随意绕过现有组件体系或样式体系。
- 对于简单的任务，不需要使用brainstorming skill来进行思考，每次使用brainstorming skill之前主动询问用户
- 实体表必须要有业务主键，使用snowflake id

# 分支要求
- main 主分支禁止直接修改
- dev 分支为开发分支，从 main 分支派生，作为功能集成分支

# 调试规范

- 后端问题必须优先分析后端日志、异常堆栈、接口输入输出和数据库状态
- 开发环境要求必须打开debug级别日志，通过观察日志来分析功能实现是否符合预期
- Celery 或异步任务问题必须分析 worker 日志、任务参数、任务状态和异常原因
- 前端问题可以分析浏览器控制台、网络请求、前端日志和实际页面行为(chrome-devtools)，小程序除外
- 涉及数据问题时，必须查询数据库验证真实数据状态
- 异常修复后必须进行一轮验证，确认问题已解决且未引入明显回归
- 禁止吞没异常，异常必须被捕获、记录并向调用方返回明确错误语义

# 日志规范

- 日志必须包含明确上下文，便于定位问题
- 日志级别必须合理区分 `debug`、`info`、`warning`、`error`
- 后端日志文件：`server/logs/backend.log`
- Celery 日志文件：`server/logs/celery.log`
- 前端日志文件：`server/logs/frontend.log`
- 排查问题时必须主动读取相关日志，不得只凭推测修改代码
- 日志不得掩盖失败，不得将错误降级成无意义成功信息
- 必须在debug级别的日志中完整体现数据流转，保证仅通过日志即可验证功能是否成功实现
- 禁止在日志中输出密码、Token、密钥、完整连接串或其他敏感信息

# 测试规范

- 后端必须保证单元测试和集成测试
- 集成测试应使用真实服务环境或等价测试实例
- 使用测试数据库进行测试，测试数据必须隔离、可重复、可清理，禁止污染生产或真实业务数据
- 前端不要求编写组件级测试
- 前端改动必须至少通过页面运行、关键交互或浏览器日志验证
- 后端改动必须优先运行相关测试；无法运行时必须说明原因
- 涉及接口、数据库、异步任务、AI 链路的改动必须验证真实调用路径

# 数据升级规范

- 涉及数据库 schema、索引、约束、枚举、默认值、字段语义、存量数据兼容或数据回填的改动，必须提供明确的数据升级方案
- 数据升级方案必须包含升级路径、回滚路径、执行顺序、兼容发布策略、验证方式和失败恢复方式
- 涉及 schema 变更时，必须提供迁移文件或等价迁移脚本；禁止只修改模型代码而不提供数据库升级路径
- 迁移脚本必须可重复检查，尽量保持幂等；不可幂等的步骤必须说明前置条件和重复执行风险
- 破坏性变更必须采用兼容式发布，不允许单步删除字段、修改字段语义、收紧非空约束或删除枚举值导致旧版本代码不可用
- 数据回填必须支持分批执行、可重入、可观测和失败恢复，禁止长事务、全表锁、无界扫描和生产高峰期高风险执行
- 新增非空字段必须先提供默认值、分阶段回填或兼容读取逻辑，确认存量数据满足约束后才能收紧约束
- 删除字段或表必须先确认无代码引用、无接口依赖、无异步任务依赖、无历史数据审计要求，并提供回滚或备份策略
- 数据升级必须包含验证 SQL、验证脚本或集成测试，用于确认 schema 状态、数据数量、关键字段完整性和业务链路可用
- 任何无法回滚、无法验证、可能污染生产数据或会造成多版本不兼容的数据升级方案，必须先告知用户并获得批准


# 禁止事项
- 禁止未经确认扩大需求范围
- 禁止未经批准新增或升级依赖
- 禁止使用临时方案替代架构内实现
- 禁止静默失败、静默兜底或吞没异常
- 禁止硬编码业务参数、路径、密钥或环境配置
- 禁止绕过 DDD、整洁架构或 feature-based 结构
- 禁止在未验证的情况下宣称问题已修复
