# 安家立业：会员开通与企业认证

> 状态：ready-for-agent
> 范围：只做安家立业。安东尼之家一行不碰。

## Problem Statement

安家立业现在是一个只有登录的骨架：用户进小程序、静默换到 openid、看到自己的用户 ID 和登录次数，除此之外什么都做不了。

而这个小程序的整个产品形态都建立在**身份分层**上：首页内容流只允许企业认证账号发布，站内私信只允许会员发起。也就是说，接下来要做的每一个板块，第一件事都是问「这个人是谁」——而现在系统答不上来。库里只有登录必需的那几列，没有会员、没有认证、没有任何身份概念。

对用户来说，眼下的问题是：**没有任何办法把自己变成会员，也没有任何办法证明自己是一家公司。** 对运营来说：**手上没有任何工具去承认或拒绝一个企业身份。**

## Solution

给安家立业补上完整的身份层，并且**只补身份层**。

用户在「我的」页能看到两个新入口：

- **会员中心** — 一键开通会员，免费、即时生效，页面上明确写着「未来将会收费」，开通后显示到期日。
- **企业认证** — 填公司全称、联系人、联系手机号，提交后进入待审核；通过后账号对外显示公司全称并带「已认证」标记；被驳回时能看到运营填的驳回理由，可以改完再提交。

运营在管理后台多出一个「安家立业」分组：一条企业认证的审核队列（通过 / 驳回 / 撤销），和一张只读的用户列表（能看到谁是会员）。

这一期做完，**用户拿到的是身份本身，还不是身份带来的权益**——站内私信和首页内容流都还没开发。这是有意为之：身份是那两个板块的前置依赖，先建好，板块开发时直接取用，不用回头改数据模型。

## User Stories

### 会员

1. 作为安家立业的用户，我想在「我的」页看到一个会员入口，以便我知道这个平台有会员这回事。
2. 作为还不是会员的用户，我想在会员中心一键开通会员，以便我立刻获得会员身份，不用等谁审批。
3. 作为还不是会员的用户，我想在开通前就看到「未来将会收费」的明确提示，以便我不会在二期开始收费时觉得被骗了。
4. 作为还不是会员的用户，我想知道开通是免费的，以便我不必担心点下去会扣钱。
5. 作为刚开通的会员，我想立刻在页面上看到自己已经是会员，以便我确认这一下点成功了。
6. 作为会员，我想看到自己的会员到期日，以便我知道这个身份能持续多久。
7. 作为会员，我想在「我的」页一眼看到会员标识，以便我不用进二级页面才能确认身份。
8. 作为已经是会员的用户，我想重复点开通时不会报错、也不会把我的到期日搞乱，以便我误触时不会产生任何后果。
9. 作为用户，我想在网络失败时看到明确的失败提示而不是静默无反应，以便我知道该重试。
10. 作为个人账号用户，我想不必先做企业认证就能开通会员，以便我作为自然人也能用上会员权益。
11. 作为企业认证账号，我想我的认证身份不会自动带给我会员身份，以便平台规则对所有人一致——反过来说，我需要知道自己还得单独开通。
12. 作为管理员，我想在后台看到某个用户是不是会员，以便我在处理咨询时知道对方的身份。
13. 作为将来接支付的开发者，我想每个会员在开通那一刻就有一条明确的到期时间，以便二期开始收费时有一条可以续费的基准线，而不是面对一批「已承诺永久有效」的老用户。

### 企业认证

14. 作为一家设计公司的运营者，我想在小程序里申请企业认证，以便我将来能在首页内容流发布我们的案例。
15. 作为申请人，我想只填公司全称、联系人姓名和联系手机号就能提交，以便我不必翻找营业执照扫描件。
16. 作为申请人，我想手机号格式填错时当场被拦住，以便我不会因为一个笔误白等一轮审核。
17. 作为申请人，我想在提交后看到「审核中」的明确状态，以便我知道申请已经递上去了、正在等结果。
18. 作为申请人，我想在审核期间不能再改动申请内容，以便管理员审的和最终生效的是同一份信息——我知道要改只能等结果。
19. 作为被驳回的申请人，我想看到管理员填写的驳回理由，以便我知道该改什么。
20. 作为被驳回的申请人，我想能修改后重新提交、不限次数，以便一次填错不会永久堵死这条路。
21. 作为认证通过的企业，我想账号对外显示的是公司全称而不是我的微信昵称，以便读者看到的是我们公司而不是「微信用户」。
22. 作为认证通过的企业，我想我的微信昵称和头像不被覆盖掉，以便认证一旦被撤销，展示能自动落回原样。
23. 作为认证通过的企业，我想在「我的」页看到「已认证」标记和公司名，以便我确认认证确实生效了。
24. 作为认证通过的企业，我想不能自己偷偷改公司名，以便这个身份对读者是可信的——我知道要改得联系运营重新提交。
25. 作为被撤销认证的用户，我想我的会员身份不受影响，以便两件事互不牵连。
26. 作为被撤销认证的用户，我想能立刻重新提交申请，以便撤销不是一道永久的门。
27. 作为个人账号用户，我想在没有认证的情况下照常浏览和使用平台，以便认证是一个可选的增益而不是准入门槛。
28. 作为申请人，我想不必先开通会员才能提交认证，以便这两件事互不为前置。

### 管理后台

29. 作为管理员，我想在后台导航里看到独立的「安家立业」分组，以便我不会把它和安东尼之家的数据搞混。
30. 作为管理员，我想看到一条企业认证的待审队列，以便我知道有多少申请在等我。
31. 作为管理员，我想按状态筛选认证记录（待审核 / 已通过 / 已驳回 / 已撤销），以便我既能处理新申请，也能回查历史。
32. 作为管理员，我想按公司名搜索认证记录，以便我能发现重名或重复提交并人工把关。
33. 作为管理员，我想在审核时看到申请人的注册时间、昵称、是否会员，以便我判断这是不是一个刚注册来蹭认证的空号。
34. 作为管理员，我想看到申请人的联系手机号明文，以便我在驳回后能直接打电话说明情况。
35. 作为管理员，我想看到同一个用户的历史申请记录，以便我发现「这个人改过三次公司名」这类风控信号。
36. 作为管理员，我想一键通过一份申请，以便日常审核足够快。
37. 作为管理员，我想驳回时必须填写理由，以便申请人知道该改什么，而不是收到一个沉默的拒绝。
38. 作为管理员，我想撤销一份已通过的认证，以便事后发现问题时能收回这个身份。
39. 作为管理员，我想知道每条记录是谁审的、什么时候审的，以便责任可追溯。
40. 作为普通管理员，我想不必找超级管理员就能审核认证，以便审核不会积压在一个人身上。
41. 作为管理员，我想在一张只读的用户列表里看到安家立业的注册用户及其会员状态，以便我掌握基本的运营数据。
42. 作为管理员，我想两次并发的审核操作不会把同一份申请通过两次，以便数据不会出现两条同时生效的认证。

### 开发与维护

43. 作为将来开发站内私信的人，我想身份判断已经有一个明确的字段可查，以便我不必在做私信时顺手重做一遍会员模型。
44. 作为将来开发首页内容流的人，我想「这个账号能不能发帖」有一个现成的答案，以便发布权限不必在业务代码里现推。
45. 作为维护者，我想安家立业的数据一行都不会写进安东尼之家的库，以便两个小程序的数据边界不被悄悄破坏。
46. 作为未来读这段代码的人，我想理解为什么存了会员到期时间却没有任何地方校验它，以便我不会把它当成 bug 顺手删掉。

## Implementation Decisions

### 身份模型：三层正交，不是等级

- **个人账号**是登录后的默认身份，不需要任何动作。
- **企业认证账号**是「存在一条生效认证」这个事实的另一种说法，不是一个独立开关。
- **会员**与前两者完全正交：企业认证不自动带来会员，会员也不是提交认证的前置。

推论：账号类型是**推导出来的**，不是存出来的。系统里不存在一个「账号类型」列——有生效认证就是企业认证账号，没有就是个人账号。这样撤销认证时不需要记得去改第二个地方。

### 数据模型（安家立业库）

**用户表新增三列**，与安东尼之家用户表同名同义（`is_member` / `member_since` / `member_expires_at`）。跨小程序保持一致命名，将来矩阵合并时不必翻译。

**新建一张企业认证申请表**，一个用户可以有多条记录，构成完整的申请历史：

| 字段 | 说明 |
|---|---|
| id | 雪花 ID，与仓库其余部分一致，出接口转字符串 |
| user_id | 申请人 |
| 公司全称 / 联系人姓名 / 联系手机号 | 申请内容，提交后不可改 |
| status | `pending` / `approved` / `rejected` / `revoked` |
| 驳回理由 | 仅 `rejected` 时有值，驳回时必填 |
| 审核人 | **存管理员用户名的文本快照，不存 ID、不建外键** |
| 审核时间 / 创建时间 | |

两个关键约束：

1. **`UNIQUE (user_id) WHERE status = 'approved'` 的部分唯一索引** —— 「一个账号最多一个生效认证」由数据库保证，不由应用层的先查后写保证，后者在并发下会漏。撤销时把该行改成 `revoked`，索引自动为下一次申请让路。
2. **同一用户同时只能有一条 `pending`** —— 同样用部分唯一索引，防止连点提交产生两条待审记录。

**公司全称不做唯一约束。** 同名公司、分公司是真实存在的，而这一期明确不做资质核验，系统没有任何依据判定谁是李鬼。改为让后台支持按公司名搜索，重名由运营人工把关。

**审核人为什么存用户名快照而不是外键**：管理员账号在安东尼之家的库里，认证记录在安家立业的库里，跨库无法建外键；存 ID 则在管理员被删除后会变成一个查不到的数字。存用户名快照的语义与订单行的商品快照一致——记录的是「审核发生的那一刻，是谁」。

### 会员开通

- 开通接口是**幂等**的：已经是会员时返回当前状态，不报错，也**不延长到期日**。延长会变成「反复点击刷有效期」的漏洞。
- 到期日在开通那一刻算出：开通时间起一年。
- **本期不校验过期**。任何需要判断会员身份的地方只看 `is_member` 这一个布尔值。这条决定单独写 ADR（见下），因为一个「写入但从不读取」的字段极易被后人当成死代码删掉，而它是二期收费唯一的历史基准线。
- 不建会员开通流水表。二期收费时流水的正确归属是支付订单表（安玺·集已有成熟形态可照搬），现在建一张没有金额、没有单号、每人只有一行的记录表，二期一定会被取代。

### 接口契约

**小程序侧**（挂在安家立业已有的 `/api/anjia` 前缀下）：

- **读取当前用户**：在已有的用户信息接口上扩展，一次返回全部身份。前端已有的 `me()` 是全局身份来源且会写本机快照，拆成两个接口意味着首屏两次请求、两份快照，外加一个「其中一个失败了怎么办」的分支。新增出参：

  ```
  isMember: boolean
  memberExpiresAt: string | null
  accountType: 'personal' | 'company'   // 由有无生效认证推导，不是存出来的
  companyName: string                    // 无生效认证时为空串
  certification: {                       // 无任何申请记录时为 null
    status: 'pending' | 'approved' | 'rejected' | 'revoked'
    companyName, contactName, contactPhone
    rejectReason: string                 // 仅 rejected 有值
    submittedAt, reviewedAt
  } | null
  ```

  `certification` 取该用户**最新的一条**记录，历史记录不出小程序接口。

- **开通会员**：一个 POST，无请求体，返回与上面同构的完整用户对象，前端直接整体替换本机快照。
- **提交企业认证**：一个 POST，带公司全称 / 联系人 / 手机号，返回更新后的完整用户对象。已有 `pending` 记录时返回业务错误，不重复插入。

两个写接口都返回完整用户对象而不是各自的局部结果，是为了让前端只有**一处**更新身份状态的代码路径。

**管理后台侧**（挂在 `/api/admin` 下的安家立业子路径）：

- 认证记录列表：按状态筛选、按公司名关键字搜索、分页；每行带上申请人的昵称、注册时间、会员状态（跨表 join，不是让前端发第二次请求）。
- 通过 / 驳回（理由必填）/ 撤销：三个动作接口。撤销只对 `approved` 有效，通过与驳回只对 `pending` 有效；状态不符时返回业务错误——管理员开着两个标签页时，第二次点击应该得到一句明确的话，而不是把记录改成一个不该有的状态。
- 用户列表：只读，分页，带会员状态。

**权限**：全部挂普通管理员依赖，不限超级管理员。认证是日常、高频、可撤销的运营动作，与「退款」那种动钱且不可逆的动作不同，卡在超管身上只会让审核积压。

### 跨库

管理后台的会话数据在安东尼之家的库，安家立业的业务数据在另一个库，一个请求同时用到两个连接池。这是 ADR 0001「单进程多库承载小程序矩阵」的既定形态，不是新增的技术债。运营是同一批人，不为安家立业另建一套后台账号。

**分页共用件需要改造**：现有的分页件把连接池写死成安东尼之家那一个。给它加一个可选的连接池参数（默认值保持不变，现有调用方零改动），而不是在安家立业这边复制一份分页逻辑——那段代码的价值恰恰在于它把两个反直觉的坑（总数不能用窗口函数、LIKE 通配符要转义）解释了一次，解释不该有第二份。

### 小程序页面

新增两个独立页面（会员中心、企业认证），「我的」页加两行入口。不做成弹层内联：会员中心要承载「未来将会收费」的提示与到期日，认证页有一个表单加四种状态（未提交 / 审核中 / 已驳回 / 已通过），塞进「我的」页会把一个三十来行的页面撑成状态机。

### 管理后台页面

导航新增「安家立业」分组，下挂「企业认证」与「用户」两页。列表、分页、状态标签沿用后台已有的组件与分页 hook，不引入新的表格形态。

### 文档动作

- **术语表**：改写「会员（安家立业）」——现有条目写的是「付费身份」，与一期免费自助开通冲突；新增「企业认证申请」条目，明确它是一条**记录**而不是一种状态。安东尼之家的会员条目**原样保留**，那处措辞冲突留给它自己那一期解决。
- **新增一条 ADR**：记录「会员到期时间在开通时写入，但一期不做任何过期校验」。这条同时满足 ADR 的三个条件——难以反悔（已发给用户的到期承诺改不掉）、不看背景会觉得奇怪（存了却不读，像 bug）、是真实权衡的结果（给永久有效则二期无法收费，做过期校验则一期凭空多一条会员会失效的链路）。

## Testing Decisions

### 什么算一个好测试

只测**外部行为**——通过接口能观察到的东西：返回的 JSON、库里落下的那一行、以及第二次调用时的反应。不测内部实现：不单独调用某个转换函数、不断言某段 SQL 长什么样、不检查某个函数被调了几次。判据很直接：**把实现整个重写一遍而外部行为不变，测试应该一行都不用改。**

### 接缝

**只有一个，而且已经存在**：HTTP 层。起真的 app、发真的请求、连真的开发库，**只把微信的 `code2session` 换成假的**——它是唯一真正的外部依赖。安家立业已有的用户登录测试就是这套形态的完整先例，照抄即可，不发明新的测试方式。

后台侧的接口走**同一个接缝**，只是多带一个测试夹具里已有的超管会话请求头；后台接口测试在仓库里也已有先例。

测试数据继续用 openid 前缀圈住，用例前后各清一次。

**前端不写测试**：整个仓库没有任何前端测试设施（管理后台没有测试运行器，小程序端没有测试文件）。为这个功能单独引一套前端测试栈，是把一个大得多的决定夹带进来，不属于这个 spec。

### 要覆盖的行为

**会员**：开通后返回值与库里都变成会员；到期日确实是开通时间起一年；重复开通不报错且到期日**一个字节都没变**；未登录调用返回 401。

**企业认证**：提交后状态是待审核；手机号格式非法被拦下；已有待审记录时二次提交被拒绝；驳回后能重新提交且历史记录仍在；通过后账号类型变成企业、公司名出接口；撤销后账号类型退回个人且**会员状态不受影响**；撤销后能立刻重新提交；对状态不符的记录执行通过 / 驳回 / 撤销返回业务错误。

**并发与约束**：数据库层面不允许同一用户存在两条生效认证——这条要直接打到库上验证，因为它由部分唯一索引而非应用逻辑保证，测应用层等于没测。

**跨库隔离**：认证记录与会员标记全部落在安家立业的库，安东尼之家的库里查不到——正反两边都断言。已有登录测试里的同类用例是这个仓库的关键资产：两个池连错库**不会抛异常**，只会安静地把数据写到别人家，靠人眼看不出来。新表必须照抄一份同样的断言。

**后台鉴权**：不带管理员会话的请求进不来；普通管理员能完成审核（验证权限没有被误收紧到超管）。

## Out of Scope

- **站内私信**。会员权益的载体，但一行都还没有。这一期只让「是不是会员」这个问题有答案。
- **首页内容流与发帖**。企业认证权益的载体，同上；发帖还牵扯人工审核队列，是独立的一块。
- **企业账号主页与关注 / 粉丝**。依赖内容流才有意义。
- **账号封禁**。安家立业的用户表连状态列都没有，而这一期没有任何内容可封，做了等于把整条内容治理链提前拽进来。
- **会员收费与支付**。一期明确免费，只在页面上提示未来会收费。
- **会员过期的校验与失效**。到期时间只写不读，理由见 ADR。
- **营业执照等资质材料的上传与核验**。明确不收——一旦收取就要承担存储与核验责任，而需求方明说不做严格核验，收了不看比不收更糟。
- **安东尼之家的会员功能**。那边的用户表虽然早有会员字段、同样没有写入入口，但不在这次范围内，一行不碰。
- **公司名的唯一性判重**。交给运营人工把关。
- **前端自动化测试设施**。

## Further Notes

**为什么先做身份、后做权益。** 做完这一期，用户开通会员后感受不到任何权益变化——这是清醒的取舍，不是遗漏。反过来做（先做私信、发帖，再回头补身份）意味着那两个板块要先假设一套身份模型、再改造，而身份模型恰恰是它们的分叉点。所以这一期必须给出**可见的反馈**来补偿：会员标识、到期日、「已认证」标记与公司名，让用户点下去有确凿的结果。

**认证从简与内容审核是配套关系。** 认证只核对公司全称、不验资质，这是需求方定的。正因为闸门宽松，将来首页内容的逐条人工审核就不能省——两者是一套设计的两半，任何一半被砍掉，另一半的风险模型就不成立。这一期不做内容审核，但做认证的人应当知道这笔账挂在哪。

**手机号明文。** 后台列表明文展示联系手机号，与安东尼之家现有做法一致（预约、服务申请里的客户手机号都是明文出后台）。理由是驳回后打电话是唯一的补救手段，脱敏只会让运营多点一次；且后台本身是超管建号、无自助注册的封闭系统。校验规则复用仓库里已有的那条手机号正则。

**关于「会员」这个词。** 它在矩阵里指两个不同的东西——安东尼之家那边是免费、由运营授予的权益状态，安家立业这边是用户自助开通、二期要收费的付费身份，两个小程序的库彼此独立。任何跨小程序的讨论都必须带上小程序名，否则一定会串。
