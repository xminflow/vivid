# 会员到期时间只写不读

安家立业的会员一期免费、自助开通（需求文档 2.2），二期起收费。开通那一刻要不要给它一个到期时间，是个只有一次机会的决定——身份一旦发出去就收不回来了。**决定：开通时把到期时间写成一年后，但一期任何地方都不校验它。** 判断一个人是不是会员，只看那个布尔标记。

于是库里出现一个「写入但从不读取」的列。这条 ADR 存在的唯一目的，就是拦住将来某个人把它当死代码删掉——它是二期收费唯一的历史基准线。

## 被否掉的选项

**给永久有效（到期时间留空）。** 一期最省事，二期最贵：那时面对的是一批「平台已经承诺过永久有效」的老用户，要么单方面撕毁承诺，要么给他们永久免费。前者是信誉损失，后者是把最早一批、也最活跃的种子用户永久排除在收入之外。

**做完整的过期校验。** 一期就凭空多出一条「会员会失效」的链路：到期前要不要提醒、失效那天用户看到什么、失效后能不能续、续了从哪天算起。这些问题在一期全部没有答案（因为没有支付），为一个一年内不会触发的场景现在就把它们答一遍，答的一定是猜的。而且一期真出现会员莫名失效，用户投诉的成本远高于「到期了但还能用」。

**开通时不写、二期再补。** 二期要给存量用户批量补一个到期时间，那个时间只能是拍脑袋定的（从注册算？从二期上线算？），而且补的那一刻就要面对「凭什么这么算」的质问。开通当时写下的时间是有据可查的事实，事后补的是编的。

## 代价与边界

**代价是一个说不通的字段。** 不看这份文档的人会认为它是遗漏的校验，甚至会「顺手修好」——加上过期判断，然后一年后一批会员集体失效。所以除了这份 ADR，代码里那一列也要有注释指回这里。

**边界：二期接支付时这条决定就作废了。** 那时到期时间从「只写不读」变成真正的有效期，同时会出现续费、支付订单、失效提醒。届时要处理的存量问题只剩一个——一期免费开通的这批人到期后怎么办（免费续、给折扣、还是直接转收费）——那是个商务决定，但至少有一条确切的日期可以谈。

**不建会员开通流水表。** 二期收费时流水的正确归属是支付订单表（安玺·集已有成熟形态可照搬）。现在建一张没有金额、没有单号、每人只有一行的记录表，二期一定会被取代，等于先造一张要迁移的表。开通时间与到期时间两列直接落在用户表上。
