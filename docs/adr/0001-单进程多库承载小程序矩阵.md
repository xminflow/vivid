# 单进程多库承载小程序矩阵

矩阵里每个小程序有自己的 appid、自己的用户体系、自己的数据库（`schema.sql` 开头就定了「一库一个小程序，openid 单列唯一」）。接入第二个小程序安家立业时，要决定它的接口跑在哪个进程里。**决定：一份代码库、一个 FastAPI 进程、每个小程序一个数据库和一个连接池**，路由按 `/api/<小程序>/` 前缀分流。

## 被否掉的选项

**复制一份 `server/` 出来独立部署。** 隔离最彻底，但微信 code2session、COS 直传签名、雪花 ID、分页、以及**管理后台的鉴权与账号管理**要各自维护一份，从此两份代码各自漂移；管理后台还会碎成两套登录态，而「一个后台管一个矩阵」是已经落地的设计（见 `website/src/app-shell.tsx` 的 NAV 分组）。

**两个小程序的表挤进同一个库，用 `app_id` 区分。** 要改用户表的唯一约束，且直接推翻已经写在 `schema.sql` 里的隔离决策。

## 代价与边界

**故障域是共享的**：安家立业的 bug 能拖垮安东尼之家的 API。接受这一点的前提是它可拆——同一个镜像起两个容器就分开了，不需要改代码。**生产环境按此拆成两个容器**（交易链路不该被 UGC 流量连累），开发环境共用一个容器。

**域名按小程序分开，即使进程共用**：`anjia.weelume.com` / `dev.anjia.weelume.com` 与 antony 的两个域名并列，Caddy 两段站点反代到同一个容器。看着冗余，但域名的可变成本远高于进程：域名写进小程序 `config.js` 发出去之后，想换要重新提审发版，还要占用公众平台每月有限的「服务器域名」修改次数；而拆进程只是改 Caddy 的 upstream，运维分钟级、小程序侧零改动。中性域名（`api.weelume.com`）才是矩阵长到四五个小程序时的终局，但迁移成本要安东尼之家发一次版来付，现在不做。

**改造范围刻意不对称**：新代码按目标形态长在 `app/anjia/` 下，`app/` 根目录的既有文件原地不动，只把真正要共享的东西抽成可传参的形式（`db` 出 `make_pool(url)` 工厂、`code2session()` 收 appid/secret 入参）。`.env` 同理——无后缀的 `DATABASE_URL` / `WX_APPID` 仍属于安东尼之家，安家立业的加 `_ANJIA` 后缀。全量对称化要同步改两份 compose 和服务器上的生产 `.env`，那是一次没有验收场景的生产配置改动，等某次本来就要动部署时顺手做。

## 悬而未决

`admin_users` / `admin_sessions` / `admin_login_attempts` 现在长在 `antony_casa` 库里，B 之下等于让一个小程序的库兼任平台库。**方向定为迁往独立的平台库 `vivid_platform`**（库先建出来放着），但接入安家立业后台页面时才实施——那时候有页面可以验证迁移是否成功，现在搬只是在动一套没有验收场景的鉴权。

**2026-08 更新：触发条件已经到了（安家立业的企业认证审核页与用户列表页），但仍然没搬。** 那两个页面的鉴权照旧查 `antony_casa`，业务数据查 `anjia`，一个请求两个池。理由是这次改动里迁库的风险与收益严重不对称：迁移要动生产 `.env`、两份 compose、部署脚本，并在**线上活着的管理员会话表**上做一次数据搬迁，而收益只是把一张表挪个位置——两个页面无论表在哪都能正常工作，也就是说迁移根本没有被这次需求验证到，「有页面可以验证」的原设想并不成立：页面验证的是页面，不是迁移。触发条件因此改写为**下一次本来就要动部署配置时顺手做**，与本文档「改造范围刻意不对称」一节里 `.env` 全量对称化的处理保持一致。
