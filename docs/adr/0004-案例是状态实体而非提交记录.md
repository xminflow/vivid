# 案例是状态实体而非提交记录

安家立业的库里已经有一张 `company_certifications`，它的注释写得很硬气：「这是一张**记录表**，不是用户表上的几个字段」——同一个用户改完重交就是一条新记录，认证状态是**查**出来的而不是存出来的。现在要建案例表，最省事的做法是照抄这个形态。**决定：不抄。案例是一行会流转状态的实体，作者被驳回后改的是同一行，不产生新记录。**

写下这条，是因为下一个打开 `schema.anjia.sql` 的人会先看到隔壁那张记录表和那段注释，然后合理地怀疑案例这里是不是抄漏了。

## 两者为什么不一样

**认证申请的价值在历史，案例的价值在当下这一版。** 管理员看得出「这个人三次提交换了三个公司名」，那本身是风控信号，合并成一行就丢了；而案例的旧版本没有任何人要看——作者改的是措辞和配图，运营审的永远是最新那一版，「他上次写的标题是什么」不构成任何判断依据。

**案例身上挂着不能跟着 ID 走掉的东西。** 浏览量已经在记（docs/adr/0002 定的那类历史基准线，见 CONTEXT.md「浏览量」），二期还会挂上点赞、收藏、评论（需求文档 AJ-04）。换一条记录就意味着这些要么清零、要么得在新旧两条之间做一次搬迁——而搬迁只有在「新记录是旧记录的续」这个前提下才成立，那正说明它们本来就该是同一行。认证申请身上什么都没挂，换一条不丢东西。

**用户心里的模型也是一行。** 「我那篇被打回来了，我改改」，不是「我再发一篇」。做成多条记录，「我的发布」列表里就会出现同一条案例的三个版本，得再造一套「只显示最新一条」的规则去把它藏起来——那是在用代码修补一个建模时就选错的形状。

## 代价

**没有审核历史。** 驳回理由随下一次审核覆盖，查不到「这条案例被驳回过几次、每次是什么理由」。接受：真正需要追溯的是账号级的行为（这个企业是不是老发广告），那应该在账号那一层做，而不是靠一条案例的版本堆去侧面推断。

**编辑已发布的案例必须打回待审核。** 这是这个形状带来的硬性配套——同一行既是「已过审的那一版」又是「作者正在改的那一版」，不打回就等于给「先发沙发图过审、再改成广告」开了个洞，人工先审后发形同虚设。前台在打回的一刻立即不可见，宁可让作者少曝光几小时，也不能让未审内容有任何一秒挂在首页。
